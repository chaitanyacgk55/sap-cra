# SAP Code Reviewer — Claude Code Project

## Purpose

An automated code review workspace for **SAP applications**:
- **SAPUI5 / Fiori** — controllers, views, manifests, i18n, OData bindings
- **CAP (CAPM)** — CDS models, service handlers, actions, projections
- **RAP** — behavior definitions/implementations, EML, service bindings
- **ABAP Cloud** — released APIs, clean-core rules, extensibility checks

## How it works

1. User uploads a file or project via `editer.html` (browser UI).
2. Files are placed under `uploads/<project-name>/`.
3. User runs `/sap-code-reviewer <project-name>` (or one of the technology-specific agents).
4. The agent **auto-detects** the SAP technology from file signatures and applies the appropriate checks.
5. Findings are written to `reports/<project-name>-findings.json`.
6. The Excel report is generated by `node scripts/export-excel.js <project-name>`.

## Technology detection (canonical rules)

The main agent classifies each uploaded file by these signals — see [docs/file-type-detection.md](docs/file-type-detection.md) for the full table.

| Technology | Signature |
|-----------|-----------|
| **SAPUI5/Fiori** | `manifest.json` with `sap.ui5`, `.view.xml`, `.controller.js`, `Component.js`, `i18n.properties`, `sap-ui-core.js` refs |
| **CAP (CAPM)** | `.cds` files, `srv/` + `db/` folders, `@sap/cds` in `package.json`, `cds.env` refs |
| **RAP** | `.abap` behaviour definition (`define behavior for`), `.abap` behaviour implementation (`class ... behaviour handler`), `service definition`, `service binding` |
| **ABAP Cloud** | `@AbapCatalog.viewSemantics`, `@AccessControl.authorizationCheck`, `CDS view entity`, released APIs (`ABAP_UNIT`, `CL_ABAP_...`), `RAP` overlap |

A single upload may contain **multiple** technologies (e.g. CAP `srv/` + UI5 `app/`). The agent reviews each layer with the right ruleset.

## Findings output format

Every finding is stored in `reports/<project>-findings.json` with this shape:

```json
{
  "project": "my-project",
  "reviewedAt": "2026-09-04T10:00:00Z",
  "technologies": ["SAPUI5", "CAP"],
  "findings": [
    {
      "id": 1,
      "severity": "High",
      "layer": "srv",
      "technology": "CAP",
      "file": "srv/catalog-service.js",
      "line": 24,
      "category": "security",
      "title": "Unsafe dynamic query construction",
      "issue": "String concatenation used to build a CQN query; bypasses parameterization.",
      "severityRationale": "User-controlled input flows directly into a SQL string with no sanitisation, giving a realistic SQL-injection path — meets the High threshold.",
      "recommendation": "Use SELECT.from(Books).where({ ID: req.data.ID }) with parameterized values.",
      "codeSnippet": "const rows = await cds.run(`SELECT * FROM ${table}`);",
      "referenceLink": "https://cap.cloud.sap/docs/node.js/cds-ql#security"
    }
  ],
  "summary": { "high": 1, "medium": 0, "low": 0, "assessment": "Blockers present" }
}
```

Severity uses **High / Medium / Low** only. Never Critical.

## Excel export

```bash
node scripts/export-excel.js <project-name>
# → reports/<project-name>-review.xlsx
```

The workbook contains sheets: **Summary**, **All Findings**, **High**, **Medium**, **Low**, and one sheet per detected technology.

*(When the user provides a sample Excel, update `scripts/export-excel.js` to match its exact column layout.)*

## What NOT to do

- Never modify uploaded source files. Reviews are **read-only**.
- Never fabricate findings. If a rule can't be verified from the code alone (e.g. destination config, transport), mark it as `PLAUSIBLE` in the JSON and say so in the recommendation.
- Never use severity `Critical` — only High / Medium / Low.
- Do not exceed 32 findings per file. Prioritize the highest-impact ones.
